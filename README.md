# HomeRunSimulator
Generated by [Rojo](https://github.com/rojo-rbx/rojo) 7.7.1.

Current work: **Stage 6A coins, Power upgrades and shop**. Coins and upgrades are **session-only and reset on leaving/rejoining**; there are no DataStore writes. Stage 5A is unchanged at Power Level 0. See the Stage 6A section below for economy rules, power timing, measured progression and validation. Earlier sections describe their original implementations.

## Getting Started
To build the place from scratch, use:

```bash
rojo build -o "HomeRunSimulator.rbxlx"
```

Next, open `HomeRunSimulator.rbxlx` in Roblox Studio and start the Rojo server:

```bash
rojo serve
```

For more help, check out [the Rojo documentation](https://rojo.space/docs).

### Markers
Markers are looked up by name (case-insensitive) under `Workspace.GameplayMarkers`; see `PitchConfig.Markers` for the accepted names (e.g. `HomePlate`, `PitcherMarker`/`Mound`, `BatterMarker`, optional `ReleasePoint`). BaseParts, Attachments and Models all work; the bottom of a part is treated as ground level. For several lanes, put each lane's markers in a child Folder named `Lane...`. Missing markers produce a warning and an invisible `Fallback_*` part under `GameplayMarkers.PitchingFallbackMarkers`. Stadium geometry is never modified.

### Simulation approach
The ball is a scripted trajectory, not a Roblox rigid body. RK4 at a fixed 240 Hz step integrates gravity, quadratic drag and Magnus lift once per pitch; rendering samples that trajectory by elapsed server time (cubic Hermite), so frame rate cannot change the path and every client renders the same curve from one replicated message. Plane crossings come from the trajectory data (with bisection refinement), not `Touched`.

Tradeoff versus native physics: native bodies give free collisions but their motion depends on network ownership, the physics solver's step and replication. That causes jitter, makes paths differ between clients, and makes reliable targeting impractical. The scripted approach gives determinism and exact targeting, but collisions such as bat contact have to be computed explicitly (Phase 2 can sample `flight.trajectory` at the swing's server time).

### Replication
One `PitchEvent` message is sent per pitch at windup start. It carries the release time as a server timestamp, the release position, velocity, spin and target. There are a few lane-state attribute changes per pitch and a result message at the crossing. Nothing is sent per frame. The windup duration (1.1 s) is the latency budget: clients that receive the message late jump straight to the correct point in the flight. Clients never send ball positions.

### Tests
- **In Studio:** with `PitchConfig.Debug.RunTestsOnStart = true` the specs run when a Studio server starts, and the results appear in Output. This includes the Instance-cleanup test that only runs in Roblox.
- **From the command line:** install [Lune](https://github.com/lune-org/lune) and run `lune run tools/run-tests.luau` from the repo root.

### Playtesting
1. Start the session with `rojo serve` and connect from Studio, or open a place built with `rojo build`.
2. Press Play. The player is moved to the batter marker and locked in place, and the camera frames the pitcher and zone.
3. Press F7 to toggle the debug overlay. It shows the zone, release point, target (green), crossing point (red), the trajectory, and a HUD with speed, flight time, target error, the server's call and the server/client crossing difference.
4. Check the Output window for lines starting with `[Pitching]`. These include the markers used, any fallback warnings, a warning if the pitcher-to-plate distance doesn't match the scale, and a log line for each pitch.

### Difficulty tiers and pacing
`PitchConfig.Difficulty.Tiers` defines `Beginner` (50-55 mph, 1.6 s windup), `Intermediate` (64-72 mph) and `Advanced` (78-85 mph, the original tuning). `PitchConfig.Difficulty.Active` selects the tier (default `Beginner`); it sets both the real release speed the solver targets and the windup/ready timing. Pitch types add a `SpeedOffsetMph` on top of the tier. There is no per-player progression yet.

### How a swing works
1. **Aim.** Each frame the mouse is turned into a camera ray (`Camera:ViewportPointToRay`) and intersected with the *contact plane* (parallel to the strike-zone plane, `ContactPlaneOffsetMeters` in front of it). The result is clamped to the aim region. The reticle is that 3D point projected back to the screen and is sized to the barrel's real vertical reach, so it is exact at any resolution or aspect ratio. Aim is never streamed to the server.
2. **Swing.** A left click (only when the previous swing has fully recovered) stamps the click with `GetServerTimeNow()`, starts the bat immediately and sends `(seq, clickTime, aimX, aimY, pitchId)`. Phases: Ready → Windup (0.05 s) → Active (0.11 s) → FollowThrough → Recovery → Ready. Everything is a pure function of server time, so it doesn't depend on frame rate.
3. **Bat geometry.** The bat is a handle capsule plus a barrel capsule that rotate about the batter's body axis in a slightly tilted swing plane. The pivot is placed so the sweet spot lands exactly on the aim point when the bat is square, so aim positions the whole swing path. During Active the angle advances at a constant rate, so the collision volume is exact. The rendered bat uses the same dimensions and pose function.
4. **Collision.** The server samples the stored 240 Hz trajectory (Hermite) over the overlap of the Active window and the flight. Conservative advancement steps by `gap / maxRelativeSpeed`, which provably cannot skip a contact at any speed, and returns the earliest touch (0.5 mm tolerance). There are no `Touched` events.
5. **Quality.** Four measured factors are each mapped to 0..1 and multiplied (weights configurable): timing (bat square time minus the time the ball reaches the aim plane), distance from the sweet spot along the bat, vertical offset from the bat axis, and collision efficiency (closing speed / relative speed). The score maps to Perfect / Great / Good / Weak; no contact is a Miss (Early / Late / Over / Under / Inside / Outside). Early contact pulls the ball and late contact pushes it, via the impact normal.
6. **Result.** On contact the server ends the pitch (`PitchServer.resolveContact`, Abort reason `Contact` with the contact time, so every client hides the ball exactly at contact), and the result is broadcast. The swinging client has already shown predicted effects using the same deterministic resolver. It replaces them with the server's result and puts the ball back if the server disagrees.

### Phase 3 hand-off
`ContactQuality.ContactResult` (in `SwingResultPayload.contact`) has these fields:
- Timing and position: contact time, time after release, contact point, ball center, bat axis point.
- Collision: impact normal, ball velocity, bat surface velocity, relative velocity, closing speed.
- Where it hit the bat: segment, distance from knob, sweet-spot offset, vertical offset.
- Swing: bat direction, swing direction, bat angle, timing error.
- Direction hints: spray-angle and launch-angle hints taken from the impact normal.
- Grading: factors, score and label.

Positions and speeds are in studs. Phase 3A added `ballSpin` (the incoming pitch spin) and replaced the temporary Phase 2 deflection with the real batted-ball flight (see Phase 3A below).

### Networking and validation
- **Requests** carry intent only. The server parses them strictly and rejects non-numbers, NaN/inf, non-integer or old sequence numbers, and aim outside the region. It also rate-limits floods (80 ms) and enforces the swing cooldown and one swing per pitch.
- **Latency compensation:** the click stamp may be rewound at most `min(0.25 s, ping + 0.06 s)`. Older stamps are clamped forward (the swing becomes later), stamps older than 1 s are rejected, and future stamps beyond 50 ms of clock noise are rejected. The ball position always comes from the server's own stored trajectory.
- **Practice swings:** swings whose Active window does not overlap the flight are accepted but don't use up the pitch.

### Tuning (beginner defaults, 50–55 mph)
Against the authoritative trajectory, with aim exactly on the ball:
- **Timing:** contact happens for timing errors of roughly ±60 ms, and Perfect is about ±20 ms.
- **Vertical:** contact is possible within about ±9 cm, which is the barrel radius plus the ball radius. The barrel collision radius is 5.5 cm for readability (a real barrel is about 3.3 cm).
- **Bat speed:** the sweet spot moves at about 47 mph.

Widen the windows with `Swing.ActiveSeconds` / angles, `Bat.BarrelRadiusMeters` and `Quality.*`.

### Tests
`Batting.spec` and `SwingValidation.spec` cover:
- perfect contact, early and late swings, wrong aim, swings that don't overlap the flight;
- frame-rate independence, millimeter bat-boundary contact, and 300 mph tunneling (with a check that a naive 60 Hz test does miss);
- sweep vs. brute force;
- duplicate and invalid requests, latency limits, cooldown and flood guard, one swing per pitch;
- pitch cleanup after contact.

### Playtesting batting in Studio
1. Press Play. The OS cursor is replaced by a ring reticle with a faint line showing where the barrel will be, and a faint strike-zone outline is drawn on the contact plane.
2. Move the mouse to put the ring where the ball will cross, then left-click as it arrives. The bat swings immediately.
3. A connected swing plays a crack, a flash, sparks and a short deflection, and the label shows the quality plus timing and sweet-spot detail. A miss shows the miss reason.
4. Press F7. The overlay shows the swing state, aim, server validation (rewind, clamping, rejections), the factors, bat and ball speeds, and whether the client prediction matched. It also draws the bat capsules at contact, the swept tip and sweet-spot path, and the contact point.
5. Output lines starting with `[Batting]` log every swing with its server outcome.

## Phase 2.5: bat alignment and miss feedback

### Visible bat
- `src/shared/Batting/BatStance.luau` decides the bat that is drawn. During the Active window it is exactly `SwingModel.activePoseAt`, the same function the collision sweep uses, so the barrel you see is the barrel that hits.
- Every other phase carries the bat to or from that pose and is continuous at each hand-off:

| Phase | Where the bat is |
| --- | --- |
| Ready | In the batter's hands, raised over the rear shoulder, drifting `Stance.PreloadFraction` of the way toward the aimed swing |
| Windup | Carried from the on-screen pose into the first collision pose |
| Follow-through | The swing continuing about the same pivot |
| Recovery | Unwound back around the front of the body into the hands (Phase 2.7) |

- `src/shared/Batting/ArmIK.luau` is a pure two-bone solver over the rig's Motor6D offsets. `src/client/CharacterGrip.luau` applies the character pose to the local character every frame, for R15 and, since Phase 2.7, R6 (see below). The rear arm is the top hand and the front arm is the bottom hand. Targets are `Stance.GripBottomMeters` and `Stance.GripTopMeters` up the handle. A target the arm can't reach clamps to a straight arm pointing at it. While no rig is bound, the bat starts from a fallback anchor near the batter marker. Turn the arms off with `Stance.ArmIK = false`.
- Collision geometry, timing, windows and quality thresholds are unchanged. The Phase 2 collision tests still pass untouched.

### Miss reasons
`MissClassifier.luau` looks at the simulated swing and the ball's real path, not the screen, and no longer uses the old 60 ms cutoff.
1. For the three mistakes (timing, vertical aim, lateral aim) it measures the error against where the ball crossed the contact plane. Each error is scaled by the same tolerance the quality score uses.
2. It re-runs the real collision sweep with each mistake corrected on its own, and reports the largest error among the corrections that would have connected. If no single correction works, it uses the largest error overall.
3. The reasons are Early, Late (timing), Over, Under (vertical aim: Over = aimed above the ball, Under = below) and Inside, Outside (lateral aim: the ball was closer in or farther out than the bat reached).
4. Misses carry an amount: seconds for Early/Late, studs for the rest. The label shows a headline (TOO EARLY, OVER THE BALL, and so on) and a hint such as "swing a little later (~45 ms)" or "aim lower (~6 cm)".
5. Swings whose Active window never overlaps the flight (more than about 100 ms late) remain practice swings with no label.

### Tests
- `BatAlignment.spec`: the drawn bat equals the collision pose while Active; the bat never snaps between phases; the bat starts at the hands; the drawn barrel overlaps the drawn ball at contact; frame-rate independence; arm IK reaches its target and clamps out-of-reach ones.
- `MissClassification.spec`: pure timing and aim cases, the playtest regression (55 ms early with a slightly low aim now reads Early, not Under), and a randomized check that every blamed mistake, once fixed, really connects.

## Phase 2.7: character animation for R6 and R15

### Why the body never moved
The Phase 2.6 binder only looked for R15 joint names (`Root`, `Waist`, `LeftShoulder`, `LeftElbow`, `LeftWrist`, ...). An R6 avatar has `RootJoint`, `Left Shoulder` / `Right Shoulder` (with a space), `Left Hip` / `Right Hip` and `Neck`, and no waist, elbow or wrist joints. Binding could never succeed on R6, so the overlay showed "waiting for an R15 rig" forever and only the bat moved. The game's avatar type is set in Studio (Game Settings > Avatar), not in this repo, so the code no longer assumes either rig.

### Layout

| Path | Runs on | Purpose |
| --- | --- | --- |
| `src/shared/Batting/RigBinding.luau` | both | Detects the rig from `Humanoid.RigType` and the joints (the joints win on a mismatch), finds the Motor6Ds, and gives an exact reason per joint when it can't bind (`LeftElbow: not found`, `Left Shoulder: Part1 not set`, `is a Weld, not a Motor6D`, ...). It also detects stale bindings after a respawn, an avatar reload replacing parts, or death breaking joints. |
| `src/shared/Batting/CharacterPose.luau` | both | Pure pose solver over joint offsets for both rigs, producing Motor6D Transforms. It follows the same bat pose that `BatStance` draws, so the body follows the authoritative swing. |
| `src/client/CharacterGrip.luau` | client | Binds the local character, writes the Transforms, re-applies them after the Animator runs, and reports diagnostics. |
| `src/server/Tests/MockRig.luau` | tests | Instance-shaped R6 and R15 characters with the standard joint offsets. |

### How the body follows the bat
- **Shared by both rigs**
  - **Torso turn.** The chest turns to face the hands as they circle the body (`TorsoFollowHands`), at most `MaxTorsoCloseDegrees` closed in the stance and `MaxTorsoOpenDegrees` open in the follow-through.
  - **Lean.** The upper body leans toward the grips when the arms would fall short.
  - **Why both are needed.** Roblox arms are short relative to the bat's circle around the swing pivot. With the old fixed 30% waist turn, the hands missed the handle by 20–40 cm during the swing.
- **R15**
  - The hips take `HipTurnFraction` of the turn and the waist takes the rest; the waist also leans.
  - Shoulders and elbows use the two-bone IK. The wrists curl around the handle (`WristWrap`), and the hand center still lands exactly on its grip.
  - The legs keep the feet planted and level while the body crouches.
- **R6**
  - The whole torso turns and leans about the hips through `RootJoint`. There is no waist.
  - The lean is mostly a forward bow about the hip line; the sideways part is capped at `R6MaxSideLeanDegrees`.
  - Each rigid arm is pointed at its grip from the shoulder. If a grip is closer than the straight arm is long, that hand slides down the handle toward the knob.
  - The legs splay into a batting stance that keeps both feet on the ground. A crouch widens the stance, and the body sinks slightly if a sideways lean would lift a foot.
  - The hands rest lower than R15's (`R6AnchorDownFraction`).
- **Recovery** now unwinds the bat back around the front of the body. The old straight blend cut the bat through the batter, and the torso flipped as the hands passed behind the back. This is presentation only.

### Update ordering
The Animator writes `Motor6D.Transform` after the render step and before physics, and parts only move to their Transforms when physics runs.
- While batting, the default `Animate` script is disabled and Animator tracks are stopped. Both are restored when batting ends or the character changes.
- The pose is written in the render step and written again in `RunService.PreSimulation`, after the Animator, so it wins even if something keeps animating.
- Overwrites are counted and logged once to Output.

### Diagnostics
- **F7 overlay, rig bound:**
  - the rig kind and `Humanoid.RigType`, and how many joints are driven;
  - missing optional joints, and any mismatch note;
  - the animation state (Animate script on or off, playing tracks, suppression);
  - whether the Transforms were applied this frame;
  - the distance from the real hand parts to where the Transforms put them ("visible" or "NOT VISIBLE");
  - Animator overwrites per second;
  - the hand-to-bat error, torso turn, lean, body shift and crouch.
- **F7 overlay, rig not bound:** the exact reason, and the retry interval.
- **Output:**
  - `[Batting] Character rig bound: R6 (Humanoid.RigType = R6), driving 5 joints: ...`;
  - each distinct binding failure;
  - stale-binding rebinds;
  - a warning if Transforms are overwritten, or if the hands stay more than 3 cm from their solved positions for over a second.

### Measured hand-to-handle error (mock rigs, CLI)
These numbers cover in-zone aims at heights 0.5–1.05 m, across the whole swing.

| Rig | Error |
| --- | --- |
| R15 | Below 0.5 cm through stance, windup and contact; below 5 cm in follow-through and recovery |
| R6 | Below 6 cm through contact; below 9 cm overall. The error is measured to the hand end of the rigid arm. |

Some cases fall short:
- **Edge aims.** The 0.3 m low and 1.3 m high-outside edges of the aim region reach about 8–12 cm (R15) and about 20 cm (R6).
- **R6 feet pivot.** Because R6 has no waist, its hips turn with the chest. The feet stay on the ground but move up to about 0.45 m during contact and 0.65 m in a full follow-through. Lowering `R6MaxTorsoOpenDegrees` or `R6MaxSideLeanDegrees` calms the feet at the cost of hands leaving the bat.

### Tests
- **`RigBinding.spec`** checks that:
  - R15 binds as R15 and R6 binds as R6, without expecting elbows or wrists;
  - a mislabelled `Humanoid.RigType` is resolved by the joints;
  - missing, unassembled and wrong-class joints are named;
  - a missing Humanoid or HumanoidRootPart gives a specific reason;
  - bindings go stale after joints are removed or broken.
- **`CharacterPose.spec`** checks, for both rigs:
  - the hands stay on the handle through the whole swing;
  - forward kinematics of the Transforms match the solve;
  - the arms move and the chest turns through contact and follow-through;
  - no joint jumps more than 15° or 4 cm per ~1.4 ms step;
  - the feet stay on the ground;
  - left-handed batters are mirrored;
  - the torso turn is continuous and capped;
  - `ArmIK = false` leaves the arms alone.

### Playtest in Studio
1. Press Play and watch Output for `[Batting] Character rig bound: ...`, which names the rig. To test the other rig, change Game Settings > Avatar > Avatar Type and play again.
2. Press F7. The rig line should say `bound` and the transforms should say `applied` and `visible`, with about 0 Animator overwrites per second.
3. Move the mouse. The hands, arms and chest should track the aim while the bat rests in the hands.
4. Swing. Check that:
   - the chest opens through contact;
   - the arms stay on the handle;
   - the follow-through turns the body;
   - recovery unwinds back to the stance with no snapping.
5. Reset the character (Esc > Reset). Output should show a stale-binding rebind, then a new bind.

## Phase 2.8: AnimationConstraint rigs (Avatar Joint Upgrade)

### What was wrong
Roblox's Avatar Joint Upgrade replaces an R15 character's Motor6Ds with `AnimationConstraint`s. Phase 2.7 accepted only Motor6Ds, so it rejected a valid R15 avatar ("R15 rig incomplete ... is a AnimationConstraint, not a Motor6D").

### How AnimationConstraint differs
| | Motor6D | AnimationConstraint |
| --- | --- | --- |
| Connects | `Part0`, `Part1` | `Attachment0`, `Attachment1` (the parts are the attachments' parents) |
| Offsets | `C0`, `C1` | `Attachment0.CFrame`, `Attachment1.CFrame` |
| Pose channel | writable `Transform` | writable `Transform` (Roblox: "the internal CFrame that is manipulated when the constraint is being animated") |
| Placement | `Part1 = Part0 * C0 * Transform * C1:Inverse()` | Keeps the attachments "offset by Transform": `Part1 = Part0 * A0.CFrame * Transform * A1.CFrame:Inverse()` |
| Physics | rigid | Force- and torque-limited unless `IsKinematic = true` ("the connected parts follow the Transform perfectly without participating in physics simulation") |

### What changed
- **Joint adapter (`RigBinding`).** Binding accepts both joint classes. `RigBinding.frame(joint)` gives one view of both: `part0`, `part1`, `c0` and `c1`. Everything downstream (`CharacterPose.read`, the client's hand-part measurement) uses it, so the pose maths is unchanged and shared.
- **Failure reasons.** These now cover AnimationConstraints: `Attachment1 not set`, `Attachment0 is not on a BasePart`, `disabled`, and `is a BallSocketConstraint, not a Motor6D or AnimationConstraint`. When several objects share a joint's name (such as ragdoll sockets or values), the first usable joint wins, and a failure explains the joint-class candidate first.
- **Kinematic joints while batting.** A force-limited constraint only steers toward a written Transform, so the limbs would lag the bat and leave the collision geometry. While batting, the client switches the bound AnimationConstraints to `IsKinematic = true` and restores each one's original value on release. Nothing is replaced, created or destroyed, the appearance is untouched, and the server never sees the change. This is set by `Stance.KinematicJointsWhileBatting`.
- **Unchanged.** Animation suppression and the PreSimulation re-apply work exactly as in Phase 2.7.

### F7 overlay
- **`rig:`** the rig kind, `Humanoid.RigType`, the joint implementation (for example `14 AnimationConstraint` or `14 Motor6D`), and how many joints were made kinematic.
- **`anim:`** the Animate script and Animator track state, whether Transforms are applied this frame, and Animator overwrites.
- **`motion:`** "VISIBLE" only when the real hand parts are within 3 cm of where the Transforms put them, plus how far the rendered hands actually travelled in the last second. Binding alone is never reported as success.
- **`grip:`** the hand-to-bat error, torso turn, lean, and body shift.

### Tests
- **`RigBinding.spec`** checks that:
  - an AnimationConstraint R15 binds, and the adapter reads the same offsets and parts as the Motor6D rig;
  - unattached, disabled and wrong-class constraints are named;
  - a same-named BallSocketConstraint earlier in the tree doesn't win;
  - a binding goes stale when an attachment is removed.
- **`CharacterPose.spec`** checks that:
  - the AnimationConstraint rig gets Transforms identical to the Motor6D rig through whole swings;
  - the hands-on-handle, forward-kinematics and visible-swing tests pass for it too.

### Needs Studio
These can't be tested from the CLI:
- whether a client-side `IsKinematic` switch is honored for your avatar;
- that the hand parts really follow (check the `motion:` line);
- that the Animator stays silent;
- that releasing restores the original joint state.

If `motion:` reads NOT VISIBLE with `14 AnimationConstraint`, the next things to check are network ownership of the limbs and whether the engine accepts the client-side `IsKinematic` change.

## Phase 3A: Batted-ball physics

A validated contact now launches a real baseball. The server turns its own contact measurements into an outgoing velocity and spin with an impulse model, integrates the flight under gravity, drag and Magnus lift, sweeps it against the stadium for the first impact, and measures the outcome. Clients rebuild the same flight from one launch message.

### Layout

| Path | Runs on | Purpose |
| --- | --- | --- |
| `src/shared/BattedBall/BattedBallConfig.luau` | both | All batted-ball tunables, SI units (see the table below) |
| `src/shared/BattedBall/FieldFrame.luau` | both | Field coordinate system from the markers, foul lines, spray angle, fair/foul |
| `src/shared/BattedBall/ImpactModel.luau` | both | Bat-ball impulse: effective bat mass, restitution, friction, spin |
| `src/shared/BattedBall/FlightPhysics.luau` | both | SI float64 RK4 integrator: gravity, drag, Magnus, spin decay, Hermite sampling |
| `src/shared/BattedBall/BattedBall.luau` | both | Contact → launch record, wire format, flight reconstruction, derived numbers |
| `src/shared/BattedBall/LandingDetector.luau` | both | Swept first-impact detection, ground vs. obstacle, distances, territory |
| `src/shared/BattedBall/HitLifecycle.luau` | both | Per-lane hit state machine (Idle → Flying → Resolved → Idle) |
| `src/shared/BattedBall/BattedBallPlayback.luau` | client | Visual ball following the flight against server time |
| `src/shared/BattedBall/BattedBallNet.luau` | both | Remote names and messages |
| `src/server/BattedBallServer.luau` | server | Authoritative launch, Spherecast caster, lane pause, broadcasts |
| `src/client/BattedBallController.luau` | client | Prediction, server reconciliation, playback, landing marker and distance label |
| `src/client/BattedBallDebugView.luau` | client | F7 overlay section and Studio-only trajectory drawing |

### What contact data is used
Everything comes from the Phase 2 `ContactResult`: impact normal, ball velocity, bat surface velocity at the contact point, distance from the knob (so the sweet-spot offset), contact time and ball center. The only addition is `ballSpin`, the incoming pitch's spin vector, which the friction model needs. The quality label and score are **never** read by the physics; they are only compared with it in tests.

### Coordinate system
- **Origin:** the home plate marker at ground level.
- **Forward (x):** horizontal, home plate → pitcher marker (toward center field).
- **Up (y):** Roblox world up.
- **Right (z):** toward the first-base side (catcher's right).
- Field coordinates are meters and right-handed (forward × up = right), so cross products match world space. Nothing assumes a world axis; the tests run on a straight lane and on a rotated, raised one.
- **Spray angle:** 0 = straightaway center field, + = right-field side, − = left-field side. **Pull angle** is relative to the batter: + = pull side (left field for a right-handed batter, from `PitchConfig.Geometry.BatterSide`).
- **Foul lines:** these come from optional markers, matched by exact name in the lane folder or `Workspace.Stadium`.
  - `LeftFoulPole` / `RightFoulPole` are used first.
  - `ThirdBase` / `FirstBase` are the fallback (see `PitchConfig.Markers`).
  - With no markers, the rulebook layout is used: each line 45° from the home → mound line. This is still marker-relative.
  - Marker lines whose opening angle falls outside 70°–110° are rejected with a logged reason.
  - The source is printed once per lane: `[BattedBall] Lane1 field frame: foul lines from ...`.
- **Units:** physics is SI. Studs only appear at the `FieldFrame` boundary through the existing `PitchConfig.Units.MetersPerStud` (0.28). Roblox `Workspace.Gravity` is not used.

### Impact model (`ImpactModel`)
The ball (a sphere) collides with a free bat, represented by its effective mass at the impact point (Nathan 2000; Cross 2011). `n` is the unit normal from the bat axis to the ball center, `v` and `V` are the ball and bat-surface velocities, `m` and `R` are the ball's mass and radius, and `I_ball = 0.4 m R²`.

```
1/M_eff = 1/M_bat + b² / I_cm                 b = impact distance from the bat's balance point
e(d)    = e_min + (e_0 − e_min) exp(−(d/w)²)  d = distance from the sweet spot
u_n     = (v − V)·n   (< 0 when approaching)
J_n     = −(1 + e) u_n / (1/m + 1/M_eff)
s_t     = tangential slip of the ball's contact point: v + ω × (−R n) − V, minus its normal part
J_t     = −(1 + e_t) s_t / (1/m + R²/I_ball + 1/M_eff),  capped at |J_t| ≤ μ J_n (then sliding)
v'      = v + (J_n n + J_t) / m
ω'      = ω + (−R n) × J_t / I_ball
```

- **Head-on hits.** The impulse reduces exactly to the batted-ball-speed formula `v_out = q v_pitch + (1 + q) v_bat`, with `q = (e − m/M_eff) / (1 + m/M_eff)`. The default wood bat has q ≈ 0.22 at the sweet spot; measured wood bats are around 0.2.
- **How contact types differ.** Each one follows from the geometry, with no label lookup:
  - **Squared up:** the normal is along the bat's motion.
  - **Under the ball:** the normal tilts up, giving a higher launch, and friction adds backspin.
  - **Topped:** the normal tilts down, giving a grounder with topspin.
  - **Inside / outside:** lower e and lower M_eff toward the handle and the tip.
  - **Glancing:** a small approach speed means a small impulse.
  - **Early / late:** the normal turns with the bat, sending the ball to the pull side or the opposite field.
- **Incoming pitch spin.** It is partly retained through the friction model, so fastball backspin reduces the batted ball's backspin, as Nathan et al. observed in 2012.
- **Numerical safety.** A separating or degenerate contact (approach ≤ 0.01 m/s, or a zero normal) exchanges no impulse, and the ball keeps its path, like a foul tip. Non-finite results fall back to the incoming state.
- **Descriptive contact type.** `BattedBall.describeContact` (Squared / Under / Topped / Inside / Outside / Glancing / Weak) is computed from the same measurements, for the HUD and logs only.
- **Simplifications.** e does not depend on speed. M_eff is also used for the tangential direction. There is no bat vibration or bending model, and the swing is not slowed by the collision.

### Flight model (`FlightPhysics`)
```
a      = (0, −g, 0) − k (Cd₀ + Cd₁ S) |v| v + k C_L(S) |v| (ω̂ × v)     k = ρ A / (2m)
S      = R |ω(t)| / |v|,   ω(t) = ω₀ exp(−t / τ)
C_L(S) = Sawicki–Hubbard–Stronge (shared with pitching: PitchPhysics.liftCoefficient)
```

- **Integration.** Fixed-step RK4 at 120 Hz on plain Luau numbers (float64), with time-dependent spin. It never uses float32 world coordinates, so accuracy does not depend on distance or on where the stadium is.
- **Sampling.** Cubic Hermite between steps, so position is a pure function of time.
- **Drag coefficient.** `Cd = 0.30 + 0.34 S`. This is Nathan's trajectory-calculator drag (0.3008 + 0.0292 per 1000 rpm) expressed through the spin factor S.
- **Reference check.**
  - **Statcast reference:** 100 mph at 28° with 2500 rpm carries 391 ft with 5.4 s of hang time (Statcast averages ≈ 390–400 ft).
  - **Convergence:** 120 Hz agrees with 960 Hz to better than 1 µm for normal hits and 10 µm at 300 mph.
- **Projection.** `fieldLanding` is where the free flight crosses plate level (`y = R`). It is a projection that ignores obstacles. The measured distance comes from `LandingDetector`.

### First impact and distance (`LandingDetector`)
- **Swept detection, in two passes:**
  - **Coarse:** sphere sweeps along 1/20 s chords. The radius is the ball radius plus the curve's largest deviation from the chord, so the swept volume contains the path.
  - **Fine:** re-sweeps of each 120 Hz segment inside a chord that hit. The first fine hit is the first impact.
  - This is equivalent to sweeping every step, which a randomized brute-force test checks. Tunneling is impossible at any speed; a 300 mph ball against a 5 cm wall is tested.
- **Surface classes:** from the hit normal (`GroundMinNormalUp` = 0.7):
  - **Ground** faces mostly up.
  - **Wall** is steep.
  - **Ceiling** faces down.
- **Outcomes:**

| Kind | When | Distances reported |
| --- | --- | --- |
| `Landed` | First impact is ground (field, terrain, raised stands) | `carryMeters` = horizontal distance from home plate to the touch point. Rolling is never added. |
| `Obstacle` | First impact is a wall or ceiling | **No carry.** We don't simulate the bounce, so `impactDistanceMeters` + `impactHeightMeters` are reported instead, labelled as such (HUD: "OFF THE WALL"). |
| `NoImpact` | Nothing was hit before the budget ended | No carry; only the labelled projection. |

- **Projection:** every outcome also carries `projectedCarryMeters`, the plate-level landing of the free flight. It is always labelled "projected" and never replaces a measurement.
- **Fair/foul:**
  - The call uses the touch point (or the projection) against the foul lines; the lines themselves are fair.
  - Landings short of the bases (27.43 m) are marked `territoryProvisional`, because the ball could still roll.
  - Home runs are **not** awarded. Nothing infers one from distance.
- **What the server ignores:**
  - all player characters;
  - `Workspace.GameplayMarkers`, and the client-only `PitchVisuals`, `BattingVisuals`, `BattedBallVisuals` and `PitchDebug` folders;
  - parts tagged `BattedBallIgnore` (CollectionService);
  - non-collidable parts (`RespectCanCollide`).

### Server-authoritative hit lifecycle
1. `BattingServer` validates and resolves the swing (unchanged).
2. On contact, `PitchServer.resolveContact` ends the pitch. Only if that succeeds (so a contact can never launch twice) does `BattedBallServer.launch` run.
3. The server runs the impact model, builds the flight from the **launch record itself**, and sweeps it with `Workspace:Spherecast`. The stadium is static, so the outcome is known at launch.
4. `HitLifecycle` pauses the lane's pitching and broadcasts one `Launch` message: the launch record (contact position, field velocity and spin as Vector3s, contact server time) plus the server's flight end time.
5. At `launchTime + endTime` it broadcasts `Resolved`, exactly once, with the outcome. It then holds `ResultHoldSeconds` (2.4 s since Stage 4, covering the camera's landing hold and return), unpauses the lane, and the normal Ready → Windup cycle continues.
6. **Edge cases:**
   - A second launch on a busy lane is refused.
   - When the batter **leaves**, the hit is cancelled and clients remove the ball.
   - A **reset or death** keeps the ball flying, since its outcome is already decided. The lane stays paused until it resolves, so a respawned batter never gets a pitch mid-flight.
   - Every path unpauses the lane, and nothing can hold it longer than `MaxFlightSeconds + ResultHoldSeconds`.
7. The lane folder's `HitState` attribute mirrors the state for debugging. It is excluded from client geometry rebuilds through `PitchNet.RuntimeLaneAttributes`.

Traffic per hit is three messages at most (`Launch`, `Resolved`, `Cancelled`), plus a few attribute changes. Nothing is sent per frame.

### Client rendering
- **Continuity.** The pitch playback is cut at the contact server time, and the batted ball starts at `t = 0` at the contact ball center. That is the same point (tested), so there is no snap.
- **Prediction.** The swinging client predicts its hit with the same deterministic code at click time. The ball stays hidden until the contact instant.
- **When the server's `Launch` arrives:**
  - **Identical launch record:** the prediction is adopted and only learns the end time.
  - **Different record:** the prediction is replaced by the server flight at the current server time.
  - **No server contact, or nothing within 1.25 s:** the prediction is removed.
- **Other clients** start from the `Launch` message.
- **Frame rate.** Position is `BattedBall.positionAt(flight, serverNow − launchTime)`, so every frame rate gives the same path.
- **Ball and landing.**
  - The ball uses the existing `BallVisual`, with a longer trail (0.35 s) and slowed visual spin.
  - It rests at the impact point for 1.6 s, then fades.
  - A landing ring with a distance billboard appears. The batter's result is shown by the Stage 4 result card (see below).
- **Units.** Feet by default; `Display.DistanceUnit = "Meters"` switches to meters.
- **Camera.** See Stage 4: the batting camera now hands off to a cinematic ball-follow camera.
- **Removed.** The Phase 2 `TemporaryDeflection` is gone.

### Camera lifecycle

```
Batting -> ContactTransition -> BallFollow -> Landing -> Returning -> Batting
   ^             |                  |            |
   +-------------+------------------+------------+-- cancel / watchdog: Returning from the current pose
```

- **Batting.** This is the existing framing. A predicted hit is registered at the click, but the camera only moves at the contact server time.
- **ContactTransition.** The camera holds for a 0.06 s beat (camera only; the ball is never paused), then blends over 0.4 s from the batting pose to the follow pose. The blend runs on its own clock, so a ball that lands during it still blends.
- **BallFollow.** The camera follows the flight (see below).
- **Landing.** This starts at `launchTime + endTime`, the server's first impact. The camera eases to a slightly wider view of the impact and holds for 1.3 s. If the server's outcome has not arrived, it waits up to 0.75 s more.
- **Returning.** The camera blends back to the batting pose over 0.85 s with a sine ease and a small upward arc. On a ~80 m fly-back the peak speed is under 3 m per 60 fps frame (tested).
- **Reconciliation:**
  - **Confirmed prediction:** keeps going.
  - **Corrected record (same pitch):** the director swaps the flight under its smoothed offsets, and the change is counted as a sync correction.
  - **Rejected or timed-out prediction:** before contact nothing happens; after contact the camera returns.
  - **Server `Cancelled`, a respawn, or leaving the lane:** the camera returns, or resets when the lane is left. Leaving the lane also restores the Roblox `Custom` camera and FOV.
  - **Watchdog:** a hit presentation is capped at `MaxHitSeconds` (20 s).
- **Lane isolation.** The director only accepts hits launched on its lane. Every event is keyed by `(laneId, pitchId)`, because pitch ids are per-lane counters.
- **Pitch coordination.** The server's post-landing hold (`ResultHoldSeconds = 2.4`) must be at least `LandingHoldSeconds + ReturnSeconds` plus 0.1 s, and a test enforces this. The next windup therefore never starts while the camera is away. Swings are ignored unless the camera is in `Batting`.

### How the follow camera frames the ball

- **Target.** The target is `BattedBall.positionAt(flight, serverNow - launchTime)`, the same call that places the ball. The camera can't lose its target because it never depends on a Part.
- **Anchor.** The camera is anchored to where the ball was `LagSeconds` ago (sampled from the trajectory, capped at `MaxLagMeters`), so the ball visibly pulls away by a bounded amount.
- **Position.** From the anchor the camera sits `Back` behind it along a smoothed horizontal heading, `Height` above, and `Side` toward the batter's side (the same side as the batting camera, so the transition doesn't swing across).
- **Climbs.** `VerticalFollow < 1` keeps the camera lower while the ball climbs, which sells height.
- **Look point.** The camera looks at the ball, plus a look-ahead along the velocity (vertical part scaled by 0.35 for a calm horizon), minus `LookDown`, which keeps the outfield below a fly ball in view.
- **Hit-type profiles.** `Profiles` are keyed by launch angle: Grounder 0°, LineDrive 16°, FlyBall 32°, PopUp 55°. Values blend linearly between anchors, so there is no cliff at a category boundary.
- **Power.** Power (exit velocity from 55 to 110 mph, clamped) adds up to 35% pullback and 6° of FOV. A 300 mph future hit stays within those limits (tested).
- **Smoothing.** The camera *offset from the ball*, the look offset and the FOV are exact critically damped springs. For a fixed target the result is identical at any frame rate. Because the offset is smoothed rather than the absolute position, speed never turns into lag, and the ball stays framed even for very fast hits.
- **Orientation.** Orientation is yaw plus pitch with zero roll (no banking, level horizon). Pitch is clamped to ±65°, which avoids the `lookAt` degeneracy and 180° flips. The heading turns at most 90°/s, and keeps its last value when the ball has under 2 m/s of horizontal speed (straight-up pop-ups).
- **Ground.** The camera stays at least 1.2 m above plate level.
- **Occlusion (client).** One raycast per frame goes from the ball to the camera, excluding characters and our visuals. The camera is clamped in front of blocking geometry immediately and eases back out over 0.5 s.

### Contact feedback

- **Intensity (0-1).** `HitPresentation.intensity` combines four measured values: exit velocity (0.45), contact quality score (0.25), bat-ball closing speed (0.15) and sweet-spot offset (0.15). The result is then scaled by a launch-angle factor that peaks at 25° and never drops below 0.6x. Before the flight is known, the quality score stands in for exit velocity. Nothing is random.
- **Tiers.** Weak (< 0.4), Solid, and Crushed (>= 0.72). The tier picks the crack sound and the spark count. Solid and Crushed also get an expanding ring aligned with the ball's outgoing direction.
- **Burst.** A flash at the real contact point, sized 0.12-0.35 m by intensity.
- **Camera impulse.** Fires only at intensity >= 0.45. It is a deterministic decaying oscillation of at most 0.9° over 0.35 s, plus an FOV punch of up to 3°. Set `Shake.Enabled = false` to turn it off.
- **No hitstop or slow motion.** The 0.06 s contact hold holds the camera only. The ball, the server clock and the physics never pause.
- **Changes to the old contact effects.** The Phase 2 flash, sparks and contact sound in `BattingPresentation` are replaced. The 0.35° camera kick is replaced by the impulse. The contact marker and quality label are kept.

### Ball flight visuals

- **Trail.** The trail grows with speed between 15 and 45 m/s: lifetime 0.18-0.45 s and opacity 25-65%. It is quantized to 8 levels, so its properties change only a few times per flight.
- **Halo.** A 9 px screen-space halo dot fades in between 8 and 22 m from the camera, so the ball stays findable at distance. It is not `AlwaysOnTop`, so walls still hide it.
- **Ball model and path.** The ball model and its path are unchanged.

### Known issues and tradeoffs

- **Contact label without a prediction.** If the server grants a hit the client did not predict and the swing result arrives before the `Launch`, that hit's card has no CONTACT chip.
- **Landing effects timing.** Landing effects trigger on the server's `Resolved` message (exact location), so they can lag the visual touchdown by one network latency.
- **Hit types are not inferred from wall geometry.** The camera does not know about fences ahead, so a deep fly ball into tall stands relies on the occlusion pull-in.
- **Spectating is out of scope.** Only the local batter's own hits drive the camera; other lanes' balls are just drawn.

## Stage 5A: Arcade batting balance

### Diagnosis and implementation

The collision sweep was working correctly. Its 5.5 cm barrel capsule plus the 3.66 cm ball radius gave about 9.2 cm of vertical contact reach. However, the cylindrical surface normal tilted rapidly as the ball moved above/below the bat axis. The impulse model amplified that tilt: at 3 cm under the ball, changing aim by 1 cm changed launch by **8.23 degrees**. Timing also changes vertical contact geometry because the existing swing plane has a 6-degree uppercut. Mouse gain was already 1 with no smoothing; changing mouse responsiveness would have hidden the geometry problem.

Power was a separate limit. The approximately 47 mph visible sweet-spot motion was scaled to approximately 56 mph for impact. With wood restitution 0.5 and effective mass approximately 0.67 kg at the sweet spot, collision efficiency `q` is approximately 0.23. The old ideal elevated benchmark reached **269 ft**. The 16 cm restitution falloff and effective-mass loss still correctly penalize handle/tip contact; the quality label itself does not control power. Increasing restitution or widening the collision volume was unnecessary.

`ImpactModel.contactNormal` now treats the contact as a configurable virtual impact surface. Resolve the actual normal into the swing plane and its upward normal; transform its signed upward component `u` using:

```text
f(u) = k*u + (1-k)*sign(u)*(max(|u|-s, 0)/(1-s))^3
k = 0.65, s = 0.45
```

Reconstruct a unit vector with the original in-plane direction. This mapping is monotonic, symmetric and continuous through its second derivative at the shoulder. Moderate offsets tilt the impulse less; near the contact boundary the normal recovers its original tilt, preserving topped balls and severe undercuts. The real approach is checked first, so an already separating contact cannot become a hit through forgiveness. The same adjusted normal drives the normal impulse, friction impulse and spin torque.

`BattedBall.computeLaunch` obtains the upward axis from the measured bat/swing directions, oriented toward lane up. Both client prediction and server authority already use this shared call. Capsule dimensions, swept collision, contact times/points, labels, swing animation, reticle mapping, pitch physics, validation, wire payloads, flight integration, landing sweeps and presentation code are unchanged.

Baseline effective bat speed increases from **1.2 to 1.68 times** the analytic swing speed (approximately 79 mph at the sweet spot). Restitution, effective mass, spin effectiveness, air density, drag, Magnus lift and the 250 J launch cap retain their previous values. No distance bonus or output launch-angle target is applied.

Rojo mappings and Studio-managed stadium assets are unchanged. There is no currency, shop, upgrade implementation, DataStore persistence or permanent progression.

`PitchServer`, `BattingServer`, `BattedBallServer` and `BatterService` call narrow gameplay hooks. Statistics never come from client predictions. The existing ball networking and lane lifecycle are extended, not replaced.

### Pacing and controls

The normal loop remains prepare → windup → pitch → swing → authoritative contact → ball follow → server result → landing presentation → smooth return → next windup.

Production `HitLifecycle` now uses a zero fixed post-result hold plus a `canFinish` gate. It resolves exactly once at the existing scheduled first-impact time, then retains the hit until the gate accepts readiness. `PitchLane.canStartPitch` also checks gameplay readiness before creating a new windup. After a validated return, `resumeAfterHit` resumes at Ready immediately, removing any leftover reset interval from a short hit; it never replaces an active pitch or revives a stopped lane. Non-contact pitch cycles retain their existing pacing.

- The default landing hold is **0.65 s**, followed by the existing **0.85 s** camera return: approximately **1.5 s** after landing on a normally delivered result, versus the former fixed 2.4 s server hold. Windup and pitch speeds are unchanged.
- Press **Space**, or click **SKIP RESULT [Space]**, during a confirmed landing result. The client requests a skip; the server validates it and authorizes presentation return. The result card/record notice dismisses and the camera returns smoothly. The ball trajectory, recorded statistics and result are not changed.
- Skip is unavailable during flight, before server confirmation, for another hit, or during an already authorized return. Duplicate skips cannot restart the camera blend. A server-confirmed result must also be present in the client camera before the control appears.
- Readiness is acknowledged after the camera is actually back, its initial lane blend is complete, and the swing has recovered. Client swings also wait for the server readiness acknowledgment, avoiding predictions during the acknowledgment race.
- The server checks the authenticated owner, current lane, living/placed character, assignment epoch, matching hit ID, result phase, request rate and a server-clock minimum return interval. Client requests contain only `(kind, laneId, epoch, hitId)`; no client distance, outcome, position or timestamp is accepted.
- A missing acknowledgment after **8 s** requests camera recovery once. It **does not** unlock the lane on a timer. A nonresponsive client remains gated; recovery still requires validated readiness.
- Death/reset stops pitching and invalidates readiness for the old character. An already launched authoritative ball continues to resolve and can update the session's statistics. Respawn requires fresh readiness. Leaving cancels an unresolved flight and removes the player's session/gate state; the next occupant gets a new epoch. Rejoining starts a new session.

`BattedBallConfig.Lifecycle.ResultHoldSeconds=2.4` remains only as a legacy standalone `HitLifecycle` fallback/comparison setting. It no longer controls production post-hit pacing. Active timings live in `GameplayConfig.Pacing`; `PresentationConfig.Timing` reads the same landing/return values so the client and server bounds agree.

### Statistics and record rules

All snapshots are private to the player. Distances are stored in meters and displayed in feet; exit velocity is mph. No statistics reset on character respawn or lane reassignment within the same server session.

| Statistic | Authoritative event/rule |
| --- | --- |
| Pitches received | One per lane-local pitch ID at authoritative release. A validated contact also registers its pitch if rewind/prediction aborted it before the release hook; these paths deduplicate. A canceled windup without contact does not count. |
| Swings | Accepted, validated swing requests, including practice swings; rejected requests do not count. Sequence numbers deduplicate. |
| Successful contacts / HUD successful hits | One per accepted server batted-ball launch ID, including fouls and subsequent canceled/unresolved flights. |
| Misses | Accepted pitch-associated swings without contact. Practice swings and watched pitches are not swing misses. |
| Contact percentage | Server-derived `contacts / accepted swings * 100`; zero with no swings. |
| Resolved fair hits / panel fair impacts | Confirmed fair ground, wall or ceiling first impacts. Provisional fair ground calls count here. Fouls and NoImpact do not. |
| Measured fair hits | Confirmed `Landed`, `Fair`, non-provisional outcomes with finite, nonnegative measured `carryMeters`. |
| Total / average fair-hit distance | Sum of eligible measured carry; average divides by **measured fair hits**, not contacts or all fair impacts. Zero until eligible carry exists. |
| Longest fair hit / session personal best | Maximum eligible confirmed carry. Neither prediction, free-flight projection nor wall impact distance can set it. |
| Over 200 / 300 / 400 ft | Eligible carries **strictly greater than** the threshold. Exactly 200 ft reaches its milestone but is not an over-200 hit. |
| Highest exit velocity | Highest finite server launch EV across accepted contacts, including foul, wall, canceled and unresolved outcomes. |

Distance eligibility is intentionally stricter than successful-contact/fair-impact counting:

| Outcome | Contact / EV | Resolved fair impacts | Carry totals, averages, records and distance thresholds |
| --- | --- | --- | --- |
| Confirmed non-provisional fair ground landing | Count | Count | Count measured carry |
| Provisional fair infield landing | Count | Count | Excluded; final territory is uncertain |
| Foul landing or foul obstacle | Count | Excluded | Excluded |
| Fair wall/ceiling first impact | Count | Count | Excluded; impact distance is not carry |
| NoImpact / unresolved trajectory | Count | Excluded | Excluded; projected distance is not a measurement |
| Flight canceled before resolution | Count | Excluded | Excluded; a late result cannot revive it |

The first positive eligible record shows **SESSION BEST ESTABLISHED**. Later improvements show **NEW PERSONAL BEST!** with distance. Ties within **0.01 m** and shorter hits do not award another record. Celebration intensity grows with the actual improvement, reaching its full restrained border pulse at a **100 ft** improvement. A 2 ft improvement gets a small pulse; baseline records use a modest separate presentation. No effect blocks input or pauses physics.

Milestones default to **200, 250, 300, 350, 400, 450 and 500 ft**, with inclusive thresholds. Each can be awarded once per player session. One hit may cross several; the UI combines them into one brief notice showing the highest newly reached milestone. Progress toward the next milestone comes from the server's session best and next-target/progress fields. Completing all milestones shows completion, not a currency reward.

### Economy and eligibility

`src/shared/Progression/ProgressionConfig.luau` owns all tuning. A confirmed, non-provisional fair ground landing pays:

```text
coins = 20 + floor(carryMeters / 0.3048 * 0.45)
```

This is linear in actual measured carry: 100 ft pays 65 coins, 200 ft pays 110, 400 ft pays 200 and 1,000 ft pays 470. There are no quality-label or random multipliers. Tiny hits still progress through the contact floor.

| Server outcome | Coins | Distance bonus / record |
| --- | --- | --- |
| Confirmed non-provisional fair ground | 20 + linear carry bonus | Measured carry only; existing records unchanged |
| Provisional short ground landing, either territory | 20 | None; final territory uncertain |
| Foul ground landing | 20 | None |
| Confirmed wall or ceiling first impact, fair or foul | 20 | None; obstacle distance is not carry |
| NoImpact / simulation budget exhausted | 0 | None; tracked/projected distance is not a landing |
| Canceled or unregistered flight | 0 | None |
| Malformed, negative, nonfinite or out-of-budget measurement | 0 | None |

The pure `PlayerProgression` reducer registers the server's accepted hit ID and consumes it exactly once on resolution/cancellation. Invalid terminal results stay terminal. `GameplayServer` supplies the same authoritative launch/result/cancel hooks used by Stage 5B statistics; no client reward/report endpoint exists. A retained last-hit high-water mark prevents replay without accumulating all completed hit IDs. Reward notifications report the amount actually credited after safe balance saturation.

### Power and purchase timing

```text
multiplier(level) = 1.12 ^ level
nextCost(level) = ceil(400 * 1.22 ^ level)
nextBenefit(level) = multiplier(level + 1) - multiplier(level)
```

The next purchase increments the numbered level by one. Each adds 12% launch speed before the safety ceiling. It extends `BattedBallConfig.Power.ArcadePowerMultiplier` in the existing shared `ImpactModel`; pitch speeds, contact geometry, normals, swing timing/poses and launch spin are unchanged. Direction still comes from physical contact, and RK4 flight still determines distance. The energy cap scales from the Level 0 250 J value by multiplier squared, bounded by the energy of a 5,000 m/s ball. Level 0's entire impact configuration and original 12-second flight budget remain exact.

The server captures current level/version **when it accepts and computes a contact**, in a non-yielding section. Buying during windup or an in-progress swing affects that contact if the purchase transaction reaches the server first. Buying after launch affects the next accepted contact; an active flight never changes. Server processing order resolves races, not the client's click timestamp. Purchases are allowed during flight at the protocol level, although the UI closes during the cinematic.

Launch packets append captured level/version to their existing velocity/spin record. Clients reconstruct from those authoritative velocity/spin values, not from their current balance or a later level. Prediction uses the latest server snapshot and captures it for that prediction. A stale-level prediction is replaced by the authoritative flight through the existing camera reconciliation. Level metadata also selects the same bounded flight budget on both peers. Legacy nine-element Level 0 packets remain readable.

`ProgressionRuntime` contains private `Update`, initialization-only `GetSnapshot`, and `Purchase` remotes. The client sends only category `Power`, monotonically increasing request sequence and expected current level. Expected level is a concurrency guard, never a power selector. The server derives ownership from the authenticated Player, checks category, finite integer sequence/level bounds, replay, stale level, a **0.35 s** purchase interval, current state, maximum level and affordability, then independently calculates price, subtracts coins and increments once without yielding. A rejected intent cannot be replayed after earning more coins. Rapid traffic prolongs the cooldown. One pending request disables further client purchases. Responses contain authoritative state and a reason; there is no optimistic debit or level increment.

Schema version **1** stores coins, session earnedCoins and powerLevel separately from statistics. Snapshots include schemaVersion, monotonically increasing version, derived multiplier/nextMultiplier/nextCost and the last hit award. Hit deduplication and purchase sequences are runtime bookkeeping rather than future persisted profile data. Subscribe-before-initialization, snapshot version guards and award hit-ID guards prevent stale initialization, out-of-order purchase responses or duplicate updates from rolling back state or replaying coin notices. Balances/counters saturate at **1e12**, below exact integer limits. The tested level limit is **40** (93.05x), a configurable numerical safety bound rather than an MLB-distance cap; future expansion requires fresh benchmarks.

### Scalability and Stage 6B boundaries

Upgraded flights stay at deterministic **120 Hz RK4**, bounded to **30 seconds / 3,600 steps** and **10,000 horizontal meters**, with the original floor handling. Swept collision now divides long engine casts into pieces no longer than **900 studs**, preserving first-hit order and distance. Launch speed/energy bounds keep the current fixed step stable. At upgraded power, the camera watchdog allows the built flight duration plus **4 seconds**, instead of returning at the old 20-second guard; ordinary Level 0 presentation remains unchanged. HUD distance derives from actual field-frame samples/server impact, and camera lag/FOV/return arcs retain their existing bounds.

The Level 40 benchmark used 2,408 integration steps and 391 logical sweeps. CLI simulate + analytic sweep measurements were roughly **33.6 ms** in the final recorded run (earlier runs reached 47.8 ms); this is a bounded synchronous workload, not a measured multi-client Studio frame budget. The high-power specs compare against 960 Hz with **0.02 m carry tolerance**, check every position/velocity sample for finiteness, reconstruct exactly over the wire, and sweep a 1 cm wall. A vacuum benchmark measures an actual ground landing beyond **10,000 ft**, within 0.02 m of the analytic flight projection. A future-stadium benchmark at 5% air density tracks **32,810 ft** before the range budget: it has **no confirmed landing and would pay zero**. Thin air is a benchmark option only, not an implemented upgrade/stadium feature.

**Current stadium limitation:** the unchanged Studio stadium has finite landing geometry. Long hits can clear it and resolve `NoImpact`, correctly paying zero rather than converting a projection into a record/reward. In the Studio smoke check, elevated Level 0 hits did this, while lower fair hits landed on the existing field and earned measured rewards. No geometry was enlarged or replaced here. Distant geometry/streaming, engine float32 world-coordinate precision, maximum concurrent-lane frame cost, longer budgets and a larger practical power range also need Stage 6B stadium/performance work.
